# orchestrate — リーダーとして並列に作業する

リーダーの Claude がペインを分け、作業役の Claude を複数動かして作業を進めるときの決まり。プロジェクトだけの値 (リポジトリ、ブランチを作る元、マージの方法など) は、各プロジェクトの CLAUDE.md か notes/ に書く。ペインの操作の書き方は、末尾の「tmux の場合」にまとめている。

## 役割

| 役 | すること |
|---|---|
| リーダー | ユーザーと話し、作業を切り出して作業役に渡し、結果を集め、記録する。大きな実装は自分でしない |
| 作業役 | 渡された 1 つの作業を、自分の worktree とブランチで行い、PR を出す |
| 係 (改善役など) | ユーザーが置くと言ったときだけ置く。目的はユーザーが言ったことだけにし、最初の仕事は観察と提案までにする。スクリプトや設定の変更などの成果物は、ユーザーが求めたときに作らせる |

## 始める前

- プロジェクトの値を CLAUDE.md・notes/ で確かめる: リポジトリ、ブランチを作る元、マージの方法、Issue の置き場、記録の置き場、作業役に読ませる設計書。書かれていなければユーザーに聞き、プロジェクトの CLAUDE.md か notes/ に書く
- 作業を Issue に書き起こす
  - 1 つの Issue は、作業役 1 人が 1 回で終えられる大きさにする
  - 内容、参照する設計書、完了の条件、範囲に含めないもの、前提 (先に終わっている必要がある Issue) を書く
  - 前提の関係は GitHub の依存関係 (blocked by) で表し、まとめの Issue を作って各 Issue を子 Issue にする
  - ユーザーの操作や判断が要る Issue には、それと分かるラベルを付ける
- 同時に渡す作業は、変更するファイルが重ならないものにする
- 前提の作業がまだマージされていないときは、そのブランチから作業のブランチを作り、PR の base をそのブランチにしてよい。前提がマージされたら、main (ブランチを作る元) の上に載せ直させる
  - 前提のブランチを消す前に、積んだ PR の base を main に変える。base のブランチを先に消すと、GitHub が積んだ PR を閉じ、base を変えられなくなる

## 配置

- リーダーは左上のペインにし、名前 (tmux では `@agent_name`) を `leader` にする
- 作業役は右の列を上下に分けて並べる。1 列は 3 段までにする。4 人以上なら右に列を足し、列の幅をそろえる
- ユーザーが置くと言った係は左下のペインにする
- 新しいペインは、フォーカスを移さずに作る
- 作業役の Claude は、ユーザーが普段使っているのと同じオプションで起動する。オプションは、動いている claude の引数 (`ps -eo args | grep claude`) で確かめる。ただし `--effort` は作業ごとに決める (「effort を決める」)

## 呼び方

- ユーザーへの報告では、画面に出ている番号で呼ぶ。ウィンドウは `w<ウィンドウの番号>`、ペインは `p<ペインの番号>` (ペインの枠の左上に出る番号) と書く
- 作業役の名前は `w`・`p` で始めない (`a1`・`a2` など)。画面の番号と取り違えないため
- 報告では「`p2` (`a1`)」のように、画面の番号を先に書く
- 作業役の名前はペインの枠にも出す (tmux では `pane-border-format` に `@agent_name` を入れてある)。ユーザーは番号でも名前でも作業役を呼んでよい。名前は振り直されないので、名前で呼ばれたほうが取り違えない
- リーダーが作業役を見分けるときは、名前と、変わらないペインの ID (tmux の `%1` など) を使う。ペインの番号は、ペインを閉じたり足したりすると振り直される
- ペインを足したり閉じたりしたら、新しいペインの番号と作業役の名前の対応をユーザーに伝える

## 作業を渡す

- 新しい作業を渡す前に、作業役の Claude を終了して起動し直す (`/clear` ではなく再起動にする)
  - 理由: 最新の CLAUDE.md と記憶を読み込み直す、前の作業のシェルが残らない、作業ごとにセッションが分かれて後から追いやすい
  - 同じ作業の続き (レビューの反映、載せ直しなど) は再起動しない
- 指示文は、前の会話を前提にせずに書く。並べる順は次のとおり
  1. `intro.md` (役割の説明)
  2. 担当: Issue の番号、ブランチ名、ブランチを作る元、変更してよい範囲、完了の確かめ方、範囲に含めないもの
  3. `worker-rules.md` (共通の決まり)
- 長い指示文は一時ディレクトリにファイルで作ってから送る
- 送ったら、待つ処理を起動し直し (「待つ」)、まだ巡回をしていなければ始める (「巡回」)

### effort を決める

作業役を起動するときに、渡す作業の難しさを見積もって `--effort` を決める。作業ごとに再起動するので、作業ごとに変えられる。

| effort | 作業 |
|---|---|
| `medium` | 手順が決まっていて、判断がほとんど要らない作業。決まった形の書き換え、文書の書き写し、手順どおりの設定の変更、載せ直し、衝突の解消 |
| `high` | 普段の実装と調査。迷ったら `high` にする |
| `xhigh` | 原因が分からない不具合の調査、設計を決める作業、多くのファイルにまたがる変更、誤りが見つけにくく戻しにくい作業 (並行処理、権限、データの移行、セキュリティ) |

- `low` は使わない。`max` は、ユーザーが指示したときだけ使う
- 決めた effort と理由を、割り当てと一緒に記録する。ユーザーへの報告にも書く (例: 「`p2` (`a1`) に #12 を `medium` で渡した。手順どおりの書き換えのため」)
- 同じ作業の続き (レビューの反映、載せ直し) は再起動しないので、同じ effort のまま進める
- 見積もりより難しいと分かったら、effort を上げる。次のときは見積もりが外れたとみなす
  - 同じ所で失敗を繰り返している
  - レビューで同じ種類の誤りが続く
  - 作業役が原因を突き止められずに止まった
- 上げるときは、作業役が作業中なら Escape で止め、同じ会話を上げた effort で開き直してから、続きを指示する。会話は引き継がれる (書き方は「tmux の場合」)

## 待つ

リーダーの Claude が動くのは、次のときだけである。

- ユーザーの入力
- 自分が Bash の `run_in_background` で起動した処理の終わり
- ペインへの文の貼り付け (作業役の承認の知らせ、全体の再起動の連絡など)
- 巡回の予定 (`CronCreate`) の時刻

作業役の Stop のフックは、作業役のペインの状態を書くだけで、リーダーには何も送らない。そのため、待つ処理が動いていない間に作業役が終わると、結果はリーダーに届かずに残る。待つ処理を切らさないことと、巡回 (次の節) の 2 つで、これを防ぐ。

- 作業役の完了は、Bash の `run_in_background` で待ち、知らせを受けてから結果を読む。待つ間に、別の作業役の結果を処理してよい
- 待つ処理は 1 つにまとめ、作業中の作業役 (指示を送った後のものを含む) 全員を対象にする。どれかの状態が `idle`・`done`・`blocked` に変わるか、ペインが無くなると終わる (書き方は「tmux の場合」)
- 待つ処理は、どれか 1 人の状態が変わると終わる。そのまま起動し直さないと、ほかの作業役を誰も待っていない状態になる。次のときは、まだ作業を持っている作業役全員を対象に、待つ処理を起動し直す
  - 知らせを 1 つ処理したとき。処理した作業役に次の指示を送ったら、その作業役も対象に入れる
  - 時間切れで終わったとき
  - 作業役が `blocked` で止まったとき。ユーザーがそのペインで答えると、作業が続くため。ただし、`blocked` のままの作業役は対象に入れない (入れると、待つ処理がすぐに終わる)。答えが入って作業が続いたことは、巡回で見つけて対象に足す
  - ユーザーが作業役に直接、追加の作業を頼んだと分かったとき
- CI やレビューの結果を待っているだけの作業役と、ユーザーの答えを待っている作業役は、対象から外す (すぐに終わってしまうため)。これらは巡回で見る

## 巡回

待つ処理が切れていても結果を取りこぼさないように、また作業役がおかしなことをしていないかを見るために、リーダーは 5 分ごとに作業役を巡回する。

### 始める・止める

- 作業役に最初の作業を渡したときに、`CronCreate` で巡回を始める
  - 式は `2-57/5 * * * *` にし、`recurring` を true にする。5 分ごとで、`CronCreate` が避けるよう求めている `:00` と `:30` に当たらない
  - プロンプトは `[巡回] orchestrate スキルの「巡回」の節に従って、作業を持つ作業役を見る` にする
  - プロンプトは必ず `[巡回]` で始める。フックはこの印で巡回の回を見分け、何も見つからなかった回は、リーダーの状態を変えず、スマホにも知らせない
- 始めたら、`CronCreate` の ID を自分のペインに記録する (書き方は「tmux の場合」)。全体の再起動で開き直されたときに、この記録を見て、巡回を作り直す指示が届く
- 作業を持つ作業役がいなくなったら、`CronDelete` で止め、記録を消す
- 巡回の予定は会話の中にしかなく、Claude が終わると消える。リーダーが開き直されたとき (`--resume`、develop の再起動の後を含む) は、`CronList` で確かめ、無ければ作り直す。待つ処理も消えているので、起動し直す
- 巡回の予定は、30 日で消える
- `CronCreate` の結果に出る次の実行の時刻は、式の分より遅れることがある。遅れの長さは予定ごとに決まっていて、5 分ごとなら最大 2.5 分である
- 巡回の予定は、リーダーが待機のときにだけ動く。リーダーが作業中なら、作業が終わるまで遅れる

### 巡回ですること

1. 作業を持つ作業役のペインを渡して、巡回の要約を読む (書き方は「tmux の場合」)。作業役ごとの見出し (名前・状態・Bash の処理が残っているか・ユーザーが使っているか・待つ処理の対象か・前の巡回から画面が変わったか) と、画面の末尾 12 行が出る。このウィンドウのほかの Claude の状態と、待つ処理が動いているかも出る
   - 費用を抑えるため、作業を持たない作業役は渡さない。画面は末尾だけを読み、それで分からないときだけ、そのペインをもう少し読む
2. 作業役ごとに、次を見る
   1. 終わっている (`idle`・`done`) のに結果を集めていなければ、集める (「結果を集める」)。ただし、`done` でも Bash の処理が残っていれば、まだ終わっていない。作業役は、その処理が終わると続きを始める
   2. ユーザーの答えを待っていれば (`blocked`、または質問を書いて止まっている)、どのペインが待っているかを、ユーザーに 1 回だけ伝える。同じ質問を 2 回は伝えない。答えはリーダーが出さない
   3. 作業中なら、おかしなことをしていないかを見る (下の「おかしなこと」)
   4. 作業中なのに待つ処理の対象になっていなければ (待つ処理が動いていないときを含む)、待つ処理を起動し直す
3. ほかの Claude の行に、作業を持たないはずの作業役が `working` で出ていれば、ユーザーが直接頼んだとみなす。作業を持つ作業役に加え、待つ処理の対象に入れる
4. ユーザーに伝えることがあれば (結果を集めた、作業役を止めた・直させた、答えを待っているペインがある)、先に自分のペインに印を付けてから伝える (書き方は「tmux の場合」)。印を付けた回は普段の回と同じに扱われ、終わると `done` になり、スマホに知らせが届く
5. 何も見つからなければ、印を付けずに、返答を 1 行 (例: 「巡回: 変わりなし」) にして終わる。この回は、フックがリーダーの状態を巡回の前の値に戻し、スマホにも知らせない

### おかしなこと

次のどれかに当たれば、止めて直させる。

- 担当の外のファイルを変更している
- 自分の worktree の外で作業している
- main に push している、またはマージしている
- 取り消せない操作をしている (ブランチ・worktree・データの削除、force push、外部への送信や投稿など)
- ほかのペインにキーを送っている
- 頼まれていない成果物 (道具、設定の変更、範囲の外の変更) を作っている
- 一時ディレクトリ (scratchpad・`/tmp`) に大きなファイルを置いている
- 同じ失敗を繰り返している
- 2 回の巡回の間に進んでいない (`前の巡回からの画面=変わっていない`)。長いビルドやテストの最中と、`run_in_background` の処理を待っている最中は除く

### 止め方と直し方

- 取り消せない操作・担当の外の操作・決まりに反する操作は、Escape で止めてから、同じ作業の続きとして直す指示を送る
- 軽いものは、作業役が待機になってから、直す指示を送る
- ユーザーが使っている作業役 (「ユーザーと作業役のやり取り」) には、送らず、止めない。ユーザーに伝える
- 止めたこと・直させたことは、ユーザーへの報告に書く

### 費用

- 巡回 1 回ごとに、リーダーは自分の会話全体を (キャッシュから) 読み直す。何も無い巡回でも、要約を読む 1 回と返答の 1 回で、API の応答が 2 回になる。1 時間に 12 回ある
- 費用を抑えるため、作業を持つ作業役がいなくなったら、すぐに巡回を止める。要約に渡すのは作業を持つ作業役だけにし、画面は末尾だけを読む

## ユーザーと作業役のやり取り

- ユーザーは作業役のペインで直接やり取りすることがある
- 作業役の質問には、ユーザーがそのペインで答える。リーダーは質問を中継しない
- ユーザーが使っている作業役には、指示を送らず、止めず、再起動もしない。使っているとみなすのは次のとき
  - そのペインにフォーカスがある
  - 入力欄にユーザーの入力がある
  - 作業役がユーザーの回答を待っている
- 次の作業は、作業役が待機中で、フォーカスが外れてから渡す
- 入力欄に薄い文字で出る文は、Claude Code が出す入力の候補で、ユーザーの入力ではない。ユーザーの決定として扱わない

### 仮で決めて進める

ユーザーが「仮で決めて進めてよい (後から直す)」と言ったときは、ユーザーの回答を待たずに進める。

- 作業役の質問には、リーダーが仮の答えを出して送る
- 指示文にも、設計で決まっていないことは作業役が仮に決めて進めてよいことを書く。共通の決まりの「ユーザーに直接聞く」より、この指示を優先させる
- 仮に決めたことは、PR 本文の「仮に決めたこと」の節と、まとめの Issue へのコメントに残す。ユーザーが後から一覧で見直せるようにするため
- PR は、ユーザーのレビューを待たずにリーダーがマージしてよい。マージの前に、CI が通っていることと、別の Claude にレビューさせて直す点が残っていないことを確かめる
- ユーザーが使用量の目安 (例: 5 時間の枠の何 % まで使うか) を決めたら、作業役の数をそれに合わせて増減する

## 結果を集める

- 作業役の報告は画面から読む。画面から消えた部分は読めないので、報告の全文は PR の本文から読む
- 作業役が見つけた不足や決めごとは、新しい Issue か既存の Issue へのコメントにする
- PR の本文に「Closes #<番号>」がなく Issue と結び付いていなければ、リーダーが足す
- PR ごとに、別の Claude (Agent ツールのサブエージェント) にレビューさせる。渡すのは PR の番号、Issue、照らし合わせる設計書、探してほしい誤りの種類だけにし、リーダーの見立ては渡さない。結果は作業役に送り、同じ作業の続きとして直させる
  - 作業役には、レビューの結果が届くまでコミットにとどめ、直しと一緒に push させてもよい。CI が長いプロジェクトで、CI を回す回数を減らせる
  - レビューの Claude に手元でビルドやテストをさせるときは、worktree とビルドの結果を一時ディレクトリ (scratchpad) に置かせず、リポジトリの `.claude/worktrees/review-<PR の番号>` に置かせ、終わったら消させる。一時ディレクトリはメモリ上 (tmpfs) にあることがあり、Rust などのビルドの結果が溜まると上限に達して、コマンドの出力が書けなくなる

## マージ

- マージの許可はリーダーが受ける。リーダーは次の順に進める
  1. プロジェクトのマージの方法でマージする。コミットメッセージに AI の署名がないことを確かめる
  2. ブランチ (手元とリモート) と worktree を消す。消す前に、未コミットのファイルがないことと、そのブランチを base にしている PR がないこと (あれば先に base を変える) を確かめる
  3. そのマージを待っている作業役に、続き (載せ直しなど) を指示する
  - 作業を終えた作業役に次に渡す作業がなければ、作業役の Claude を終了してペインを閉じる。閉じたら、新しいペインの番号と作業役の名前の対応をユーザーに伝える
  4. ほかの開いている PR が main と衝突していないか (`mergeable`) を確かめ、衝突していれば作業役に載せ直させる。`Cargo.lock` のような全員が触るファイルは、1 つマージするたびにほかの PR と衝突しやすい。載せ直すたびに CI が回り直すので、早く知らせる
- PR を作った作業役がそのセッションのまま待っているときは、ユーザーがそのペインで直接マージを頼んでもよい。その場合も、リーダーは PR の状態を見て、後に続く作業を進める
- ユーザーが作業役のペインで PR を承認すると、作業役がリーダーのペインに知らせる (worker-rules.md)。知らせを受けたら、承認がそのペインで本当に入力されたかを画面で確かめ、レビューの指摘が残っていないかを見てからマージする。指摘が残っていれば、直してからマージするかをユーザーに聞く

## 記録

- プロジェクトの記録 (notes/、CLAUDE.md の現況) はリーダーだけが書く。作業役どうしの書き込みがぶつからないようにするため
- 決まったこと、分かったこと、作業役への割り当ては、その都度記録する

## 全体の再起動の連絡を受けたとき

ユーザーが別のペインで「すべての Claude Code を再起動して」と頼むと、そのペインから「[全体の再起動]」で始まる連絡が届く (`restart-claude` スキル)。連絡の指示に従う。

- 作業役に新しい作業を渡すのをやめ、`tmux-agents restart-workers <自分のペイン>` を Bash の `run_in_background` で動かす。待機で、Bash ツールの処理が残っていない作業役だけが、同じ会話のまま開き直される。ペインの ID・名前・effort は変わらない。作業中の作業役は待たずに外れ、そのまま作業を続ける
- 終わったら、出力 (再起動した作業役と、飛ばした作業役とその理由) を記録に残し、返答を短くして止まる。止まると、リーダー自身も同じ会話のまま再起動される
- 待つ処理が動いていても、止まってよい。リーダーの再起動で待つ処理は消えるが、開き直した後に作り直す
- 巡回をしていたリーダーには、開き直した後に「[巡回] 再起動で、巡回の予定 (CronCreate) と待つ処理が消えました。…」が届く。これに従って、巡回の予定と待つ処理を作り直し、その回の巡回をする
- 再起動のあとは、ユーザーの指示を待つ。作業役の割り当てと記録はそのまま使える

## tmux の場合

コマンドは `tmux` スキルの「Claude を作業役として動かす」に従う。ここには、この手順で使う決まりだけを書く。Herdr を使うときは `herdr` スキルを読む。

- 作業役の名前はペインの `@agent_name` に入れる。状態はペインの `@agent_state` (`idle`・`working`・`blocked`・`done`) で見る
- effort は、起動のコマンドの `--effort` で渡す。zsh の別名 `claude` が先に `--effort high` を付けるが、後に書いた `--effort` が効く。effort を上げて同じ会話を開き直すときは、`tmux-agents restart <作業役のペイン> <段階>` を `run_in_background` で動かす (`tmux` スキル)
- 再起動するときは、`/exit` を送ってシェルに戻ったことを `#{pane_current_command}` で確かめる。次に `@agent_state` を `starting` にしてから Claude を起動し、`idle` になるのを待つ (前の `idle` が残っているため)
- 指示を送る前に `@agent_state` を `sent` にし、`idle`・`done`・`blocked` のどれかになるのを待つ
- 待つ処理は、`~/.config/tmux/bin/tmux-agents wait <秒> <ペイン>...` を Bash の `run_in_background` で動かす。秒は 3600 にする。状態は 2 回続けて同じ値を読んでから終わる (フックが書き込む途中の値で終わらないため)。終わると、渡したペインごとに「ID 名前 状態」を出す。時間切れなら「時間切れ」を出して 1 で終わる
  - 動いている間は、リーダーのペインの `@waiting` に「pid 対象のペイン」が入る。巡回の要約は、これで待つ処理が動いているかを見る
  - `tmux-agents wait` だけを動かしている Bash の処理は、全体の再起動で「残っている処理」に数えない。ほかのコマンドと 1 つの Bash にまとめると数えられ、リーダーが再起動の対象から外れる
- 巡回
  - 始めたら `tmux set -p -t "$TMUX_PANE" @patrol <CronCreate の ID>`、止めたら `tmux set -p -t "$TMUX_PANE" -u @patrol`。`tmux-agents restart` (全体の再起動を含む) は、開き直したペインに `@patrol` があれば、巡回を作り直す指示を「[巡回]」で送る
  - 巡回のプロンプトを手でペインに入れるときは、`send-keys -l` で打ち込む。`paste-buffer -p` で貼ると、Claude Code が文を `<pasted_content>` で包んでフックに渡すので、`[巡回]` が先頭に来ず、普段の回として扱われる
  - 巡回の要約は `~/.config/tmux/bin/tmux-agents patrol <作業を持つ作業役のペイン>...` で読む。ペインは ID で渡す。前の巡回の画面と比べるため、作業役のペインの `@patrol_hash` に画面の要約の値を書く。経過時間が入る行 (`…` を含む行) と Tip の行は、比べるときに除く
  - ユーザーに伝えることを見つけたら、`tmux set -p -t "$TMUX_PANE" @patrol_report 1` で印を付ける。フック (`tmux-agents hook`・`notify.sh`) は、この印が無い巡回の回 (プロンプトが `[巡回]` で始まる回) を、状態を変えず、通知もしない回として扱う
- develop を再起動すると、ペインの ID が振り直され、`@agent_name` などのペインのオプションは戻らない。リーダーは、`list-panes` で作業役のペインを引き直し、自分のペインの `@agent_name` を `leader` に、作業役のペインの `@agent_name` を元の名前に付け直す。作業役は、リーダーに知らせるときに `@agent_name` でリーダーのペインを探すため
- ユーザーが使っているペインとみなすのは、次のどちらかのとき
  - `#{pane_active}`・`#{window_active}` が 1 で、`#{session_attached}` が 1 以上
  - 入力欄にユーザーの入力がある。入力欄の文が入力の候補かどうかは、`capture-pane -e` で文に `ESC[2m` (薄い文字) が付いているかで見分ける
- 配置が崩れたら、`select-layout` に配置の文字列 (`#{window_layout}` の形、先頭に 4 桁のチェックサム) を渡して戻す。`select-layout -o` は直前の 1 回しか戻せない
