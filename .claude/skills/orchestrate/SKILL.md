# orchestrate — 司令塔として並列に作業する

司令塔の Claude がペインを分け、作業役の Claude を複数動かして作業を進めるときの決まり。プロジェクトだけの値 (リポジトリ、ブランチを作る元、マージの方法など) は、各プロジェクトの CLAUDE.md か notes/ に書く。ペインの操作の書き方は、末尾の「tmux の場合」にまとめている。

## 役割

| 役 | すること |
|---|---|
| 司令塔 | ユーザーと話し、作業を切り出して作業役に渡し、結果を集め、記録する。大きな実装は自分でしない |
| 作業役 | 渡された 1 つの作業を、自分の worktree とブランチで行い、PR を出す |
| 係 (改善役など) | ユーザーが置くと言ったときだけ置く。目的はユーザーが言ったことだけにし、最初の仕事は観察と提案までにする。スクリプトや設定の変更などの成果物は、ユーザーが求めたときに作らせる |

## 始める前

- プロジェクトの値を CLAUDE.md・notes/ で確かめる: リポジトリ、ブランチを作る元、マージの方法、Issue の置き場、記録の置き場、作業役に読ませる設計書。書かれていなければユーザーに聞き、プロジェクトの CLAUDE.md か notes/ に書く
- 作業を Issue に書き起こす
  - 1 つの Issue は、作業役 1 人が 1 回で終えられる大きさにする
  - 内容、参照する設計書、完了の条件、範囲に含めないもの、前提 (先に終わっている必要がある Issue) を書く
  - 前提の関係は GitHub の依存関係 (blocked by) で表し、まとめの Issue を作って各 Issue を子 Issue にする
  - ユーザーの操作や判断が要る Issue には、それと分かるラベルを付ける
- 同時に渡す作業は、変更するファイルが重ならないものにする
- 前提の作業がまだマージされていないときは、そのブランチから作業のブランチを作り、PR の base をそのブランチにしてよい。前提がマージされたら、main (ブランチを作る元) の上に載せ直させる
  - 前提のブランチを消す前に、積んだ PR の base を main に変える。base のブランチを先に消すと、GitHub が積んだ PR を閉じ、base を変えられなくなる

## 配置

- 司令塔は左上のペインにする
- 作業役は右の列を上下に分けて並べる。1 列は 3 段までにする。4 人以上なら右に列を足し、列の幅をそろえる
- ユーザーが置くと言った係は左下のペインにする
- 新しいペインは、フォーカスを移さずに作る
- 作業役の Claude は、ユーザーが普段使っているのと同じオプションで起動する。オプションは、動いている claude の引数 (`ps -eo args | grep claude`) で確かめる

## 呼び方

- ユーザーへの報告では、画面に出ている番号で呼ぶ。ウィンドウは `w<ウィンドウの番号>`、ペインは `p<ペインの番号>` (ペインの枠の左上に出る番号) と書く
- 作業役の名前は `w`・`p` で始めない (`a1`・`a2` など)。画面の番号と取り違えないため
- 報告では「`p2` (`a1`)」のように、画面の番号を先に書く
- 作業役の名前はペインの枠にも出す (tmux では `pane-border-format` に `@agent_name` を入れてある)。ユーザーは番号でも名前でも作業役を呼んでよい。名前は振り直されないので、名前で呼ばれたほうが取り違えない
- 司令塔が作業役を見分けるときは、名前と、変わらないペインの ID (tmux の `%1` など) を使う。ペインの番号は、ペインを閉じたり足したりすると振り直される
- ペインを足したり閉じたりしたら、新しいペインの番号と作業役の名前の対応をユーザーに伝える

## 作業を渡す

- 新しい作業を渡す前に、作業役の Claude を終了して起動し直す (`/clear` ではなく再起動にする)
  - 理由: 最新の CLAUDE.md と記憶を読み込み直す、前の作業のシェルが残らない、作業ごとにセッションが分かれて後から追いやすい
  - 同じ作業の続き (レビューの反映、載せ直しなど) は再起動しない
- 指示文は、前の会話を前提にせずに書く。並べる順は次のとおり
  1. `intro.md` (役割の説明)
  2. 担当: Issue の番号、ブランチ名、ブランチを作る元、変更してよい範囲、完了の確かめ方、範囲に含めないもの
  3. `worker-rules.md` (共通の決まり)
- 長い指示文は一時ディレクトリにファイルで作ってから送る
- 完了は Bash の `run_in_background` で待ち、知らせを受けてから結果を読む。待つ間に別の作業役の結果を処理してよい
  - 複数の作業役を 1 つの処理で待つ。どれかの状態が `idle`・`done`・`blocked` に変わったら終わるようにする。状態はフックが書き込むので、一度だけ `idle` を読んだ場合は書き込みの途中のことがある。2 回続けて同じ値を読んでから終わる
  - CI やレビューの結果を待っているだけの作業役は、待つ対象から外す (すぐに終わってしまうため)

## ユーザーと作業役のやり取り

- ユーザーは作業役のペインで直接やり取りすることがある
- 作業役の質問には、ユーザーがそのペインで答える。司令塔は質問を中継しない
- ユーザーが使っている作業役には、指示を送らず、止めず、再起動もしない。使っているとみなすのは次のとき
  - そのペインにフォーカスがある
  - 入力欄にユーザーの入力がある
  - 作業役がユーザーの回答を待っている
- 次の作業は、作業役が待機中で、フォーカスが外れてから渡す
- 入力欄に薄い文字で出る文は、Claude Code が出す入力の候補で、ユーザーの入力ではない。ユーザーの決定として扱わない

### 仮で決めて進める

ユーザーが「仮で決めて進めてよい (後から直す)」と言ったときは、ユーザーの回答を待たずに進める。

- 作業役の質問には、司令塔が仮の答えを出して送る
- 指示文にも、設計で決まっていないことは作業役が仮に決めて進めてよいことを書く。共通の決まりの「ユーザーに直接聞く」より、この指示を優先させる
- 仮に決めたことは、PR 本文の「仮に決めたこと」の節と、まとめの Issue へのコメントに残す。ユーザーが後から一覧で見直せるようにするため
- PR は、ユーザーのレビューを待たずに司令塔がマージしてよい。マージの前に、CI が通っていることと、別の Claude にレビューさせて直す点が残っていないことを確かめる
- ユーザーが使用量の目安 (例: 5 時間の枠の何 % まで使うか) を決めたら、作業役の数をそれに合わせて増減する

## 結果を集める

- 作業役の報告は画面から読む。画面から消えた部分は読めないので、報告の全文は PR の本文から読む
- 作業役が見つけた不足や決めごとは、新しい Issue か既存の Issue へのコメントにする
- PR の本文に「Closes #<番号>」がなく Issue と結び付いていなければ、司令塔が足す
- PR ごとに、別の Claude (Agent ツールのサブエージェント) にレビューさせる。渡すのは PR の番号、Issue、照らし合わせる設計書、探してほしい誤りの種類だけにし、司令塔の見立ては渡さない。結果は作業役に送り、同じ作業の続きとして直させる
  - 作業役には、レビューの結果が届くまでコミットにとどめ、直しと一緒に push させてもよい。CI が長いプロジェクトで、CI を回す回数を減らせる
  - レビューの Claude に手元でビルドやテストをさせるときは、worktree とビルドの結果を一時ディレクトリ (scratchpad) に置かせず、リポジトリの `.claude/worktrees/review-<PR の番号>` に置かせ、終わったら消させる。一時ディレクトリはメモリ上 (tmpfs) にあることがあり、Rust などのビルドの結果が溜まると上限に達して、コマンドの出力が書けなくなる

## マージ

- マージの許可は司令塔が受ける。司令塔は次の順に進める
  1. プロジェクトのマージの方法でマージする。コミットメッセージに AI の署名がないことを確かめる
  2. ブランチ (手元とリモート) と worktree を消す。消す前に、未コミットのファイルがないことと、そのブランチを base にしている PR がないこと (あれば先に base を変える) を確かめる
  3. そのマージを待っている作業役に、続き (載せ直しなど) を指示する
  - 作業を終えた作業役に次に渡す作業がなければ、作業役の Claude を終了してペインを閉じる。閉じたら、新しいペインの番号と作業役の名前の対応をユーザーに伝える
  4. ほかの開いている PR が main と衝突していないか (`mergeable`) を確かめ、衝突していれば作業役に載せ直させる。`Cargo.lock` のような全員が触るファイルは、1 つマージするたびにほかの PR と衝突しやすい。載せ直すたびに CI が回り直すので、早く知らせる
- PR を作った作業役がそのセッションのまま待っているときは、ユーザーがそのペインで直接マージを頼んでもよい。その場合も、司令塔は PR の状態を見て、後に続く作業を進める
- ユーザーが作業役のペインで PR を承認すると、作業役が司令塔のペインに知らせる (worker-rules.md)。知らせを受けたら、承認がそのペインで本当に入力されたかを画面で確かめ、レビューの指摘が残っていないかを見てからマージする。指摘が残っていれば、直してからマージするかをユーザーに聞く

## 記録

- プロジェクトの記録 (notes/、CLAUDE.md の現況) は司令塔だけが書く。作業役どうしの書き込みがぶつからないようにするため
- 決まったこと、分かったこと、作業役への割り当ては、その都度記録する

## tmux の場合

コマンドは `tmux` スキルの「Claude を作業役として動かす」に従う。ここには、この手順で使う決まりだけを書く。Herdr を使うときは `herdr` スキルを読む。

- 作業役の名前はペインの `@agent_name` に入れる。状態はペインの `@agent_state` (`idle`・`working`・`blocked`・`done`) で見る
- 再起動するときは、`/exit` を送ってシェルに戻ったことを `#{pane_current_command}` で確かめる。次に `@agent_state` を `starting` にしてから Claude を起動し、`idle` になるのを待つ (前の `idle` が残っているため)
- 指示を送る前に `@agent_state` を `sent` にし、`idle`・`done`・`blocked` のどれかになるのを待つ
- ユーザーが使っているペインとみなすのは、次のどちらかのとき
  - `#{pane_active}`・`#{window_active}` が 1 で、`#{session_attached}` が 1 以上
  - 入力欄にユーザーの入力がある。入力欄の文が入力の候補かどうかは、`capture-pane -e` で文に `ESC[2m` (薄い文字) が付いているかで見分ける
- 配置が崩れたら、`select-layout` に配置の文字列 (`#{window_layout}` の形、先頭に 4 桁のチェックサム) を渡して戻す。`select-layout -o` は直前の 1 回しか戻せない
